# Services


## Backend
This is the Backend Posts Service. It is responsible for talking to the Posts DB, and exposing an internal HTTP API for managing Posts.

### Environment Variables
| Environment Variable | Purpose                                                 |
|----------------------|---------------------------------------------------------|
| PORT                 | Which port will the service listen on for HTTP requests |
| DB_USER              | Username for connecting to the Backend DB               |
| DB_PASSWORD          | Password for connecting to the Backend DB               |
| DB_HOST              | Hostname/Network address for the Backend DB             |

### Image
The Backend service image is available at `rmitdominichynes/sdo-2025:backend`.

### Dependencies
The Backend service depends on a PostgreSQL database, with the required migrations. An image for this has been provided, available at `rmitdominichynes/sdo-2025:db`.

### Database Configuration
The PostgreSQL Databse container also requires some environment variables to be configured.

|  Environment Variable        |  Purpose                                                  |
|------------------------------|-----------------------------------------------------------|
|  POSTGRES_USER               | Username for the Backend Service to use to connect        |
|  POSTGRES_PASSWORD           | Password for the Backend Service to use to connect        |
|  POSTGRES_DB                 | "posts"                                                   |

## Frontend
This is the Frontend Posts Service. It is responsible for serving a UI to users over HTTP. This UI allows them to view and manage Posts.

### Environment Variables
| Environment Variable | Purpose                                                 |
|----------------------|---------------------------------------------------------|
| PORT                 | Which port will the service listen on for HTTP requests |
| BACKEND_URL          | Fully qualified URL for reaching the Backend Service    |

### Image
The Frontend service image is available at `rmitdominichynes/sdo-2025:frontend`.


# Running The Services Locally (In Docker)
1. Run `docker compose up -d` to start the two services, and a postgres database container.
2. View the Frontend Posts Service at `http://localhost:8081`, and the Backend Posts Service at `http://localhost:8080`.

# Deploying The Services

The services can be deployed to EC2. 

Each container needs: 
- The correct environment variables configured (refer to the above sections)
- Security Groups will need to be configured to allow traffic to reach the instances. 
    - They will also need to be configured to allow the instances to talk to each other, if the services are deployed on different instances.
    - The PostgreSQL database receives inbound traffic on port `5432`
    - The ports used by the Backend and Frontend services are configurable through the `PORT` environment variable. Otherwise, it will default to port `8081`.

# Section A - Overview

This repository automates the deployment of the Posts application’s **Backend** and **Database** on AWS EC2 using **Terraform** (infrastructure) and **Ansible** (configuration). The goal is to avoid human error and make deployments repeatable and testable.

## Repository layout

terraform/ # EC2 and Security Group (20GB root volume)
- main.tf # Providers and AWS resources
- outputs.tf # Terraform outputs (public_ip, dns, ssh_connect)
- variables.tf # Input variables (e.g. key_name)

ansible/ # Ansible playbook, variables and inventory
- playbook.yml
- group_vars/all.yml # image names, ports, DB creds
- inventory.ini # generated by scripts
- requirements.yml # community.docker collection

scripts/ # helper scripts
- deploy.ps1 / .sh # deploy infrastructure and config
- refresh.ps1 / .sh # resync inventory with current IP
- verify.sh # health and container checks
- destroy.ps1 / .sh # teardown infrastructure

## Design decisions (what and why)

- **Default VPC:** Specs permits default VPC. Keeps infrastructure minimal.
- **Security Groups:**  
  - Port 22 (SSH) -> open for provisioning.  
  - Port 8000 (Backend) -> publicly reachable.  
  - Port 5432 (Postgres) -> not publicly exposed. DB is only reachable inside a Docker network (`posts_net`). This secures the DB while still allowing the Backend to connect.
- **Disk size:** Root volume set to 20 GB (gp3) to prevent Docker pull failures due to low space.
- **No AWS credentials in repo:** AWS provider uses a local profile (`academy`).
- **Idempotency:** Re-running `terraform apply` and `ansible-playbook` leaves infra unchanged if already configured.

## Prerequisites

- Terraform >_ 1.6
- AWS CLI
- Ansible
- curl
- Windows: PowerShell 7+ and WSL (Ubuntu) for running Ansible
- AWS Academy profile configured locally (`academy`)
- EC2 PEM key in `~/.ssh` with permissions `chmod 600`

## Automated deployment (recommended)

### Powershell (Windows)
```powershell
# From repo root
pwsh .\scripts\deploy.ps1
# This applies Terraform, writes ansible/inventory.ini with the new IP,
# copies your PEM into WSL and fixes permissions.
```

### Bash (Linux/WSL)
```bash
chmod +x scripts/deploy.sh
scripts/deploy.sh
# This applies Terraform, writes ansible/inventory.ini, and runs Ansible.
```

## Manual deployment (alternative)

### Terraform
```bash
cd terraform
terraform init
terraform apply -auto-approve -var="key_name=a2-key3"
terraform output  
```

### Ansible
```bash
# install Ansible collection
ansible-galaxy collection install -r ansible/requirements.yml

# ensure ansible/inventory.ini contains the EC2 IP and PEM path
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml
```

## How to verify
```bash
# Backend is publicly reachable
curl -I http://<EC2_IP>:8000/

# Optional: quick API smoke
curl -X POST "http://<EC2_IP>:8000/posts" \
  -H "Content-Type: application/json" \
  -d '{ "title": "Hello", "body": "from EC2" }'
curl "http://<EC2_IP>:8000/posts"

# Check containers and network via Ansible ad-hoc:
ansible -b -i ansible/inventory.ini app -m shell -a "docker ps"
ansible -b -i ansible/inventory.ini app -m shell -a "docker network inspect posts_net >/dev/null && echo posts_net: OK"
```

## Troubleshooting
- SSH denied: Ensure var.key_name in Terraform matches your PEM, chmod 600 on PEM.
- WSL can’t SSH but PowerShell can: Likely VPN/firewall blocking WSL -> :22.
- No space left on device: Re-apply Terraform (ensures 20 GB disk).
- AWS auth errors: Refresh AWS Academy credentials. Test with aws sts get-caller-identity.

## Clean up (avoid costs)
```bash
# PowerShell
pwsh .\scripts\destroy.ps1
# Bash
chmod +x scripts/destroy.sh
scripts/destroy.sh
```

# Section C - Three tier on separate EC2s and GitHub Actions

**What changed**
- Terraform now creates **three EC2 instances**: `a2-frontend-ec2`, `a2-backend-ec2`, `a2-db-ec2`.
- **Security Groups**:
  - Frontend SG: public **:80** (HTTP) and SSH for provisioning.
  - Backend SG: **:8000** only from **Frontend SG** (not public).
  - DB SG: **:5432** only from **Backend SG** (not public).
- Ansible deploys:
  - DB container on DB host (no published ports).
  - Backend container on Backend host (wired to DB via **DB private IP**).
  - Frontend container on Frontend host (published **80:8081**, `BACKEND_URL=http://<backend-private-ip>:8000`).
- GitHub Actions workflow **runs on `main` only** and performs: Terraform apply, generate inventory from outputs, Ansible deploy. **No AWS creds in repo**.

**How to verify**
1. Open the latest run in **Actions** and check:
   - `Terraform apply` succeeded and printed FE/BE/DB IPs.
   - `Ansible` tasks ended `ok/changed` without failures.
2. From your machine:
   ```bash
   curl -I http://<frontend-public-ip>
   curl -I http://<backend-public-ip>:8000 || echo "backend not public"
```
